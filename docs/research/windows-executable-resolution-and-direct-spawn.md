# Windows executable resolution and direct spawn

Research for [Adopt a library for Windows executable resolution and direct spawning, or keep hand-rolling the shim parser and App Execution Alias fallback?](https://github.com/secantdev/secant/issues/207), 2026-09-23. Source observations are from Secant `65ea27f`, OpenCode `1ead9e3d7f`, and the linked upstream sources. The available host is macOS; no new Windows execution was performed.

## Recommendation

Keep Secant's present `which` + narrowly recognized npm `.cmd` shim + `where.exe` fallback, with direct `node:child_process` spawn. Treat this as **frozen at these two compatibility cases**, not as a general Windows command interpreter. Reject an unrecognized `.cmd` or `.bat` as `unsupported-shim`. Reopen when a concrete second shim format must run, an App Execution Alias fails the Windows release acceptance check, or a library can return a native executable plus arguments without invoking `cmd.exe` and can see aliases. The first trigger is already stated in [the process Module's growth-limit comment](https://github.com/secantdev/secant/blob/65ea27ff10ebd5d8f9ec2896202c8e29a5023306/src/process/process.ts#L24-L49).

The [runtime decision](https://github.com/secantdev/secant/issues/21#issuecomment-5497308855) requires resolving npm shims to their real target and spawning directly, never through `shell: true`. The [dependency growth rule](https://github.com/secantdev/secant/blob/65ea27ff10ebd5d8f9ec2896202c8e29a5023306/docs/agents/dependencies.md) allows hand-rolled code when its supported scope is fixed. Secant's implementation recognizes one `%_prog%` npm template, resolves its interpreter, and routes every `.cmd`/`.bat` result through the shim rule; a Windows `which` miss invokes `where.exe` and takes its first result ([source](https://github.com/secantdev/secant/blob/65ea27ff10ebd5d8f9ec2896202c8e29a5023306/src/process/process.ts#L67-L215)). The real alias path is assigned to Windows package smoke; unit tests inject `where.exe` output ([test source](https://github.com/secantdev/secant/blob/65ea27ff10ebd5d8f9ec2896202c8e29a5023306/tests/process/resolve-executable.test.ts#L11-L15)).

## Alternatives checked

- **`cross-spawn@7.0.6` (OpenCode's choice):** Its Windows parser redirects non-`.exe`/`.com` targets, including `.cmd`, to `cmd.exe` even when `options.shell` is false ([source](https://github.com/moxystudio/node-cross-spawn/blob/v7.0.6/lib/parse.js#L30-L75)). Its resolver uses `which@2`, with no alias-specific handling ([source](https://github.com/moxystudio/node-cross-spawn/blob/v7.0.6/lib/util/resolveCommand.js)). OpenCode wraps it for process launch and separately wraps `which.sync`; neither wrapper handles AppExecLink ([process](https://github.com/anomalyco/opencode/blob/1ead9e3d7f02661176fd46d7bcac7f6b7be3b52d/packages/opencode/src/util/process.ts), [which](https://github.com/anomalyco/opencode/blob/1ead9e3d7f02661176fd46d7bcac7f6b7be3b52d/packages/core/src/util/which.ts)). **Reject:** it breaks the direct-target requirement and does not remove the alias fallback.
- **`execa`:** Its current docs say `.cmd` runs without setting `shell: true`, but its implementation substitutes `cmd.exe /d /s /c` for non-native files ([Windows docs](https://github.com/sindresorhus/execa/blob/main/docs/windows.md), [source](https://github.com/sindresorhus/execa/blob/main/lib/arguments/command-file.js#L19-L54)). Its resolver uses `which-command`; no documented AppExecLink support was found ([source](https://github.com/sindresorhus/execa/blob/main/lib/arguments/command-file.js#L68-L87)). **Reject for shim launch:** “no `shell: true`” is weaker than “no shell-spawned shim.”
- **`node:child_process` alone:** Node documents that `.cmd` and `.bat` cannot launch under direct `execFile`; documented launch routes use a shell or explicitly spawn `cmd.exe` ([docs](https://nodejs.org/api/child_process.html#spawning-bat-and-cmd-files-on-windows)). Keep it as Secant's primitive after direct-target resolution; it supplies no shim interpretation or alias-aware discovery.
- **`Bun.which` / `Bun.spawn`:** `Bun.which` is a documented built-in PATH resolver, but it does not document npm-shim interpretation or AppExecLink behavior ([docs](https://bun.sh/docs/runtime/utils#bunwhich)); `Bun.spawn` is a spawn primitive ([docs](https://bun.sh/reference/bun/spawn)). This is not a demonstrated replacement and would add a Bun API call to target source under [ADR 0030's allowlist](https://github.com/secantdev/secant/blob/65ea27ff10ebd5d8f9ec2896202c8e29a5023306/docs/adr/0030-ship-the-shell-as-a-bun-compiled-single-file-executable.md#runtime-neutrality).
- **npm `read-cmd-shim`:** This library **does exist**; it synchronously extracts a destination path from npm `.cmd`/`.ps1`/Cygwin wrappers ([README](https://github.com/npm/read-cmd-shim#readme), [source](https://github.com/npm/read-cmd-shim/blob/main/lib/index.js#L5-L26)). It does **not** return the `_prog` interpreter, shebang arguments, or environment setup written by [`cmd-shim`](https://github.com/npm/cmd-shim/blob/main/lib/index.js#L56-L112), and offers no lookup or alias handling. It is a candidate parser component if support grows, but using it now still needs custom interpreter policy and `where.exe`. The M3/M5 audit statement that `cmd-shim` only writes shims overlooked this separate package.
- **Windows `where.exe`:** Keep as narrow discovery fallback. Microsoft's docs specify current-directory/PATH search and `PATHEXT` completion ([docs](https://learn.microsoft.com/en-us/windows-server/administration/windows-commands/where)). Node's AppExecLink report records `fs.statSync` returning `EACCES` while `lstatSync` works ([nodejs/node#36790](https://github.com/nodejs/node/issues/36790)); Secant's pinned `which@6` calls `isexe`, whose Windows implementation calls `statSync` ([which](https://github.com/npm/node-which/blob/v6.0.1/lib/index.js), [isexe](https://github.com/isaacs/isexe/blob/v4.0.0/src/win32.ts)). Secant invokes `where.exe` without a shell, then still applies the shim rule to its first result ([source](https://github.com/secantdev/secant/blob/65ea27ff10ebd5d8f9ec2896202c8e29a5023306/src/process/process.ts#L89-L120)).

## Lookup caveats

Microsoft documents `where` as searching the current directory before `PATH`. This is **not a difference from Secant's primary resolver**: pinned `which@6.0.1` prepends `process.cwd()` on Windows before PATH ([`which` source](https://github.com/npm/node-which/blob/v6.0.1/lib/index.js#L16-L27), [`where` docs](https://learn.microsoft.com/en-us/windows-server/administration/windows-commands/where)). After `which` misses, an ordinary current-directory `.exe` should not first appear through `where`; an AppExecLink unreadable by `stat` could. Windows can exclude the current directory from bare-name search via `NoDefaultCurrentDirectoryInExePath`; both resolvers' ordinary current-directory behavior deserves a Windows scenario if Secant later promises exact `CreateProcess` search parity ([Microsoft API](https://learn.microsoft.com/en-us/windows/win32/api/processenv/nf-processenv-needcurrentdirectoryforexepathw)). This is not evidence that the alias fallback must be removed.

`where` also accepts `*` and `?` patterns, whereas `which` searches a literal command ([Microsoft docs](https://learn.microsoft.com/en-us/windows-server/administration/windows-commands/where), [`which` source](https://github.com/npm/node-which/blob/v6.0.1/lib/index.js)). **Inference:** if an authored command contains wildcard characters and `which` misses, the fallback might return a different executable. Constrain the fallback to literal names or verify this in the Windows acceptance matrix before claiming exact resolver parity. This is a small guard/test follow-up, not a reason to replace the whole resolver.
